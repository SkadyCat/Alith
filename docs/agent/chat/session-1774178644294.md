这是一个**竞态条件 (Race Condition)**：

1. **第一次启动**：Canvas22 会话运行，`child1` 进程启动，`sess.runId = r1`
2. **第二次启动**：
   - `start` handler 杀掉 `child1`，立即创建新 `runId = r2`
   - 调用 `checkProxyAvailable()` **（异步！）**
   - 如果代理缓存命中，`.then()` 在微任务队列中执行 `doSpawn`，设置 `sess.process = child2`
   - **紧接着** `child1` 的 `close` 事件在宏任务中触发
   - close handler 执行 `sess.process = null`、`sess.status = 'idle'` → **覆盖了刚启动的 child2！**
   - 广播 `status: 'idle'` → 前端认为会话已结束

**修复方案**：在 `start` handler 中立即设置 `sess.runId = runId`，在 close handler 头部加竞态保护，发现 `runId` 已被替代则跳过状态重置。

## Bug 分析报告

**根本原因：竞态条件（Race Condition）**

### 问题时序

```
第二次 start 请求：
  1. 杀掉 child1 (SIGTERM)
  2. 创建新 runId = r2
  3. checkProxyAvailable()  ← 异步！
  ↓ 微任务（代理缓存命中时）
  4. doSpawn() → sess.process = child2, sess.status = 'running'
  ↓ 宏任务（child1 退出事件）
  5. child1.close 触发：
     sess.process = null  ← 覆盖 child2！
     sess.status = 'idle' ← 覆盖 'running'！
     broadcast(status:'idle') ← 前端误认为会话已结束！
```

**新会话为什么正常**：不存在旧进程，无竞态。

### 修复内容（`pyagent_server.js`）

1. **`start` handler**：创建 `runId` 后**立即** `sess.runId = runId`（作为抢占锁），确保旧 close handler 能感知到已被替代
2. **`close` handler 头部**：加 `if (sess.runId !== runId) return` 竞态保护
3. **`error` handler 头部**：同样加保护

修复已保存，热重载生效。
