# 技能节点框架 — 设计思路文档

> 版本：v1.1 · 作者：爱丽丝 · 日期：2026-03-16

---

## 一、核心哲学：效果即图，组合即创作

### 问题原点

传统技能系统的最大瓶颈在于 **"硬编码效果爆炸"**：  
每一种技能 = 一段独立代码。当技能数量从 20 增长到 200，维护成本指数级上升，且跨技能的组合效果完全无法预测。

**节点图框架的核心假设**：
> 任何技能效果，都可以分解为：**触发源 → 传播载体 → 行为修饰 → 最终效果** 的有向链路。

所有"复杂效果"都是这条链上节点的组合，而不是一个新的特例。

## 二、框架分层模型

```
┌───────────────────────────────────────────────────────────┐
│                     技能(Skill Graph)                       │
│                                                             │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐             │
│  │  SOURCE  │───▶│ DELIVERY │───▶│ MODIFIER │             │
│  │ (何时触发)│    │ (如何传播)│    │ (怎样运动)│             │
│  └──────────┘    └──────────┘    └──────────┘             │
│                                       │                     │
│              ┌────────────┐           ▼                     │
│              │ CONDITION  │◀──── ┌──────────┐              │
│              │  (条件门)  │      │  EFFECT  │              │
│              └────────────┘      │ (最终效果)│              │
│                    │             └──────────┘              │
│                    └──────────────────▶ (触发新链路)        │
│                                                             │
│  辅助节点：FILTER(过滤对象) · TRANSFORM(数据变换)           │
└───────────────────────────────────────────────────────────┘
```

### 七类节点的职责划分

| 节点类型 | 英文 | 回答的问题 | 典型子类 |
|---------|------|----------|---------|
| **触发源** | Source | 技能什么时候/如何激活？ | 主动施法、被动触发、光环脉冲、联动反应 |
| **传播载体** | Delivery | 效果怎么抵达目标？ | 投射物、范围、光束、瞬发、持续场、召唤 |
| **行为修饰** | Modifier | 载体的运动行为如何变化？ | 分裂、穿透、弹跳、追踪、链式、螺旋 |
| **最终效果** | Effect | 抵达目标后发生什么？ | 伤害、DoT、治愈、增益、减益、控制、标记 |
| **条件门** | Condition | 什么情况下才执行后续？ | 命中时、暴击时、击杀时、标记叠满时 |
| **目标过滤** | Filter | 哪些对象受影响？ | 仅敌方、仅盟友、仅低血量、按元素筛选 |
| **数据变换** | Transform | 数值如何在节点间转换？ | 放大、衰减、元素转换、随机化 |

## 三、三条数据总线：理解连线的本质

节点之间的连线（Edge）不是简单的箭头，它承载三种不同性质的信息：

```
exec 总线  ─────────────────────────────────────────────────
           控制流。"现在轮到你执行了"。
           类比：函数调用链。A.exec → B.exec 表示 A 执行完后调用 B。

signal 总线 ────────────────────────────────────────────────
           事件总线。"某件事发生了，你可以选择响应"。
           格式：signal:on_hit / signal:on_kill / signal:on_crit
           类比：观察者模式。Delivery 触发 on_hit，Condition 监听并决定是否放行。

data 总线  ─────────────────────────────────────────────────
           数据流。传递数值、目标列表、元素引用等结构化数据。
           格式：data:number / data:element / data:target_list
           类比：函数参数传递。
```

### 为什么分三条总线？

**单一总线设计的陷阱**：如果只有一种连线，"伤害数值传递"和"执行顺序控制"就会混在一起，导致：
- 图结构难以分析（无法静态分析执行顺序）
- 循环检测困难（exec 可以检测环，data 允许有向无环）
- 调试困难（不知道某条线传的是控制还是数据）

三总线设计让每条线的**语义清晰可见**，图的结构即是文档。

## 四、复杂效果的涌现：组合爆炸是设计目标

### 4.1 线性链：最基础结构

```
[主动施法] →exec→ [投射物] →exec→ [伤害效果]
```
= 普通攻击技能

### 4.2 事件分叉：命中后触发额外链路

```
[主动施法] →exec→ [投射物] →exec→ [伤害]
                      │
                 signal:on_hit
                      │
                      ▼
                  [条件:命中] →exec→ [DoT灼烧]
```
= 火球术：主体伤害 + 命中附加灼烧

### 4.3 二阶触发：条件嵌套条件

```
[击杀触发Source] →exec→ [范围Delivery] →exec→ [标记Effect]
                               │
                          signal:on_hit
                               │
                               ▼
                         [条件:标记叠满] →exec→ [范围Delivery] →exec→ [爆炸伤害]
```
= 毒爆连锁：击杀→毒标→5层爆炸。**两个 Delivery 串联** = 二阶技能

### 4.4 多输入汇聚：联动反应

```
[技能A 触发 on_kill] ──────────────────────────────┐
                                                     ▼
[技能B 的 reaction Source，监听 A 的 on_kill] →exec→ [范围Delivery] →exec→ [神圣伤害]
```
= 技能 B 响应技能 A 的事件。**跨技能联动**，构成套装/组合流派的基础

### 4.5 数据注入：动态参数

```
[Transform: 目标剩余血量 → 数值] →data:number→
                                               ▼
[效果: 伤害，base 从 data:number 读取]
```
= 剩余血量越低伤害越高的"处决"效果

## 五、平衡机制：复杂度权重系统

### 5.1 权重分配原则

| 节点类型 | 权重 | 设计意图 |
|---------|------|---------|
| source | 0 | 触发方式不影响强度本身 |
| delivery | 3 | 多一个 delivery = 多一层伤害来源，权重最高 |
| modifier | 2 | 修饰让一个 delivery 变得更强 |
| effect | 2 | 每个额外效果都是真实收益 |
| condition | 1 | 条件有随机性，适当折扣 |
| transform/filter | 1 | 辅助节点，弱化权重 |

### 5.2 稀有度权重上限

```
普通 ≤ 10 权重   →  1~2 个 delivery + 少量修饰
魔法 ≤ 14 权重   →  可接受 modifier + 条件触发
稀有 ≤ 18 权重   →  二阶触发，条件链开始出现
史诗 ≤ 24 权重   →  复杂多层结构
传奇 ≤ 32 权重   →  多联动，多 delivery
传说 ≤ 48 权重   →  几乎无限制的组合图
```

这套机制保证：**稀有度 = 技能图的拓扑复杂度**，而不是单纯数值通胀。

### 5.3 冲突规则

某些修饰节点组合在物理上无意义：

```json
"ModifierConflicts": {
  "split": ["fork"],    // 分裂和分叉都是"复制弹道"，语义重复
  "homing": ["spiral"]  // 追踪轨迹与固定螺旋轨迹互斥
}
```

引擎在验证图时自动检测冲突，禁止这类连接。

## 六、可扩展性设计：如何添加新效果

### 6.1 添加新子类型

只需在对应类型的 subtype 字典中追加一个新条目：

```json
// 新增 "投影克隆" 修饰节点
"ModifierSubtypes": {
  "mirror": {
    "count": 2,
    "mirror_axis": ["horizontal","vertical"],
    "delay_ms": 200
  }
}
```

无需修改任何其他节点的定义。

### 6.2 添加新 signal 类型

扩展 PortTypes 枚举：

```json
"signal:on_shield_break",   // 护盾破碎时
"signal:on_teleport",       // 位移完成时
"signal:on_summon_death"    // 召唤物死亡时
```

新信号自动可被所有 Condition 节点监听，无需专属代码。

### 6.3 添加新元素

只需在 elements.json 追加一行，元素的弱点/抗性矩阵自动生效：

```json
{ "id": "storm", "name": "风暴", "weakness": ["earth"], "resistance": ["lightning"], ... }
```

所有 Delivery 和 Effect 的 element 字段自动支持新元素。

## 七、运行时执行模型

### 7.1 图的求值顺序（拓扑排序）

引擎在技能激活时执行以下流程：

```
1. 找到 Source 节点（入度为 0 的 exec 节点）
2. 按拓扑序执行 exec 链路上的所有节点
3. 每个节点执行时：
   a. 从 data 入边收集参数
   b. 执行自身逻辑（生成实体、计算伤害、应用状态）
   c. 向 signal 出边广播事件
   d. 向 exec 出边传递控制权
4. signal 事件被注册在一个"事件队列"中
5. exec 链完成后，处理事件队列（触发 Condition 节点的后续链）
```

### 7.2 Delivery 节点的特殊生命周期

```
Delivery 生成实体（投射物/范围/光束）
     │
     ├──→ 实体存活期间持续广播 signal（on_hit, on_expire...）
     │
     └──→ 实体消亡时触发 signal:on_expire
```

这意味着 **Delivery 节点是持续存在的信号源**，不是一次性的函数调用。

### 7.3 标记（Mark）系统的双端协议

Mark Effect 和 Condition:on_consume_mark 构成一个**标记协议**：

```
施加端：Effect:mark → 在目标身上注册 mark_id="poison_mark"，叠加层数
消费端：Condition:on_stack_max(mark_id, count) → 层数达标时触发
        Condition:on_consume_mark(mark_id) → 消耗标记触发（清零）
```

通过这种间接机制，两个完全不同的技能（或同一技能的不同链路）可以跨时间协作完成复杂效果。

## 八、当前框架的边界与 v2.0 方向

### 8.1 当前限制

| 局限 | 描述 | v2.0 解决方向 |
|------|------|-------------|
| Transform 节点未实现 | 数据变换子类型还是空壳 | 定义：scale/clamp/random/conditional_branch |
| Filter 节点缺少正式定义 | 只有 enemies_only 示例 | 定义完整的目标筛选规则集 |
| 无跨技能上下文共享 | 技能间数据传递只能靠 mark | 引入全局 BlackBoard 节点 |
| 无时序控制节点 | 无法做"延迟0.5秒后执行" | 引入 Delay 节点 |
| 无随机分支 | 固定的 chance 参数，无真正分支 | 引入 RandomSwitch 节点 |
| 无法组合多个元素 | 单一 element 字段 | 支持元素混合：fire+ice = steam |

### 8.2 v2.0 核心新增节点

```
BlackBoard     ─ 全局状态存取（跨技能数据共享）
Delay          ─ exec 延迟（"0.5秒后执行下一节点"）
RandomSwitch   ─ 按权重随机选择其中一条 exec 出边
Loop           ─ 在 exec 链中重复执行 N 次（用于多段伤害）
GroupScope     ─ 将子图打包成可复用的模块（技能片段库）
ElementMixer   ─ 两种元素融合，产生新元素效果
```

## 九、设计总结

**这个框架的本质是：将技能设计语言从"写代码"变成"搭积木"。**

积木（节点）的核心设计原则：
1. **单一职责**：每个节点只做一件事
2. **接口标准化**：端口类型决定可连接性，不是节点类型
3. **组合爆炸是目标**：N 种节点 × M 种连接方式 = N×M 种可能效果
4. **权重约束平衡**：组合越复杂，需要越高稀有度，体现技能的稀缺感
5. **可视化即文档**：节点图本身就是技能逻辑的完整描述

最终目标：**设计师无需写代码，就能设计出任意复杂的技能效果**。
